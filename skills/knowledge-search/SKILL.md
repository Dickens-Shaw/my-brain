# 从个人知识库找答案

知识库是一个 Obsidian Vault，里面有 5000 多篇收藏的文章和书籍章节。这个 skill 不用向量索引，靠文件搜索定位文档，再读原文回答。

**用简体中文回答。**

## 什么时候用这个 skill

用户问的是「我可能存过的东西」时：

- 「Vue 的响应式原理是怎么实现的」
- 「我收藏的文章里有讲 Webpack 缓存的吗」
- 「之前存的那篇讲 TypeScript 类型体操的」
- 「React 性能优化有哪些做法」

**不要用**：问题可以在当前代码库里直接回答（这个仓库的源码、依赖、文档），或者用户问的是通用知识、和他的收藏无关。判断依据是「答案可能在他存的东西里」。

## 检索脚本

脚本在仓库根目录的 `scripts/kb-search.mjs`。先确认仓库位置：

```bash
ls scripts/kb-search.mjs 2>/dev/null || KB_SEARCH="$(git rev-parse --show-toplevel)/scripts/kb-search.mjs"
```

下面的例子都写成 `node scripts/kb-search.mjs ...`，在仓库根目录执行。如果当前目录不是仓库根，用上面算出来的绝对路径。

脚本输出按相关度排序的候选文档，每个都带标题、路径、命中的词数比例，以及 Obsidian 深链。

`--paths-only` 只输出相对路径，适合接着传给别的工具。

参数：

| 参数 | 作用 |
| --- | --- |
| `--limit N` | 返回条数，默认 10 |
| `--scope library\|books\|all` | 限定范围，默认 all（Library + Books） |
| `--outline` | 输出小标题结构和行号，用来定位该读哪一段 |
| `--paths-only` | 只输出路径 |
| `--vault PATH` | 覆盖 Vault 路径，默认读 `.env` 的 `VAULT_PATH` |

**它比裸 grep 强在四件事**：

- 按「命中了几个查询词」排序，不按出现次数。一篇提到三个关键词的文档排在一篇反复出现同一个词但没提另外两个的前面。
- 标题命中的权重更高。人写代码时也是先看标题。
- 中文按二元组匹配，「持久化缓存」能找到写了同样内容的文档，不需要分词完全对齐。
- 去掉了「怎么」「如何」「哪些」这类停用词。这些词描述的是问题，不是主题，强行要求它们出现会让查询什么都匹配不到。

**注意 `Weak match` 警告。** 当最相关的候选只覆盖了大部分查询词时，脚本会提示库很可能没有这个主题。出现这个警告时：

- 先换词重试（见第三步）。
- 仍然不行就直接告诉用户库里没有，**不要拿一个只沾边的文档硬答**。grep 永远能返回点什么，警告是唯一的信号。

判断标准很简单：**如果第一名的标题和你的问题不是同一件事，那就是没有。**

## 检索流程

### 第一步：搜

先把用户的问题改写成**具体的检索词**。

- 「怎么让 webpack 打包更快」→ 搜 `webpack 构建性能` 或 `webpack 持久化缓存`
- 「Vue 响应式怎么实现的」→ 搜 `Vue 响应式原理`
- 「那个更新页面的东西」→ 先搜 `页面更新` 或 `nextTick`

规则：

- **优先搜技术名词的英文形式**。`nextTick`、`webpack`、`useMemo` 命中率高过中文转写。
- **一次搜 2-4 个词，不要塞整句话**。词太多会拉低每个词的覆盖率。
- 先搜宽的，命中太多再搜窄的。

```bash
node scripts/kb-search.mjs "webpack 持久化缓存" --limit 8
```

### 第二步：读候选文档

从上往下看结果，判断哪几篇真正相关。**不要把所有结果都读一遍**——每读一篇都在烧 token。

按这个顺序挑：

1. `match` 是 100% 且标题命中的——几乎一定是它。
2. 标题就是答案的——比如搜「CSS 3D perspective」，标题写着「CSS 与 3D 之 perspective」。
3. 主题对得上但标题不精确的——比如搜「webpack 性能」，标题是「webpack5 知识体系近万字总结」，这种长文通常覆盖整个主题，值得读。

然后**先看结构，再读正文**。直接读全文是最费上下文的做法——一篇三万字的文章读下来可能 50KB，而答案往往只在其中两个小节里。

```bash
node scripts/kb-search.mjs "前端 脚手架" --limit 3 --outline
```

`--outline` 只输出每篇文档的小标题结构和行号，几百字节就能判断哪篇值得读、该读哪一段：

```
## 从入门到精通，100行代码构建你的前端CLI脚手架之路
   path:  Library/1.Web/mock-8/....md
   size:  19526 bytes, 1080 lines
   headings (line numbers, for a read with offset):
         31  # 从入门到精通，100行代码构建你的前端CLI脚手架之路
         58  ## 二. cli脚手架核心功能
        190  ### 2.5 处理创建模版命令
        388  ### 2.7 实现下载模版
```

看完结构，用 Read 工具**只读相关的行**（`path` 是相对 Vault 根目录的路径，Vault 路径看 `.env` 的 `VAULT_PATH`）：

- 标题结构里出现了和你的问题对应的章节 → 只读那几个章节，行号范围从 outline 里取
- 文档是扁平结构（提示 `no headings`）→ 读开头 4000 字节，通常够了
- 标题就对上了 → 读开头 3000~4000 字节

**读够回答就行，不要读完整个文件。** 实测这个流程能把一次问答从 36KB 压到 8KB。

如果读完相关章节还是没答案，说明这篇不相关，换下一篇或换关键词重搜。

### 第三步：换词重试

第一次没命中时，**不要放弃，也不要原样再搜一次**。换的是检索策略，不是措辞：

| 情况 | 换什么 |
| --- | --- |
| 搜中文没结果 | 换英文技术名词 |
| 搜英文没结果 | 换中文说法，或换成更通用的词（`webpack` → `构建工具`） |
| 命中太多、都不相关 | 加限定词，或者换成更具体的词 |
| 命中太少 | 去掉限定词，用更宽的词先定位领域 |

最多重试三次。三次都没有，就直接告诉用户「你收藏的内容里没找到这个」，**不要编**。

## 读文档的技巧

**找到答案就停。** 读到答案所在的段落就够，不用读完整篇。

**先 outline 再读。** 这是省上下文最有效的一步：`--outline` 给你行号，你按行号读，而不是通读。

**书和文章的区别。** `Books/` 下的是书籍章节，一章一个文件，主题集中，通常整章读完更好。`Library/` 下的是单篇文章，可能很长，可能有无关部分。

**读之前先想清楚要什么。** 知道自己要「下载模板的实现」就不要读「发布到 npm」那一节。

## 直接用 grep 的情况

脚本不适用时，直接用 Grep 工具：

- 找一个精确的字符串，比如一个错误信息、一个函数名
- 找某个特定 URL
- 已知文件在哪，只需要确认内容

```bash
grep -rn "特定字符串" ~/Documents/"Obsidian Vault"/Library --include="*.md"
```

## 回答

- **给出出处**。说清楚答案来自哪篇文档、什么标题、什么来源（微信收藏 / 掘金 / 书）。用户收藏了几年，需要知道哪篇值得回去细读。
- **标注是收藏的旧内容**。收藏里有很多两三年前的文章，技术和结论可能已经过时。遇到明显过时的结论（比如 Vue 2 的写法）要指出来。
- **库里有矛盾时，两个都说**。不同文章对同一件事的说法不一样，把分歧讲清楚，不要自己选一个。
- **答案不在库里就说不在**。收藏不是搜索引擎，没有就是没有。

## 注意

- Vault 在仓库外（`~/Documents/Obsidian Vault`），不在仓库里。别在仓库里找文档。
- `Notes/`、`Projects/`、`Daily/` 是用户自己写的，内容少但最重要，搜到了一定要优先读。
- 不要修改 Vault 里的任何文件。这个 skill 只读。
