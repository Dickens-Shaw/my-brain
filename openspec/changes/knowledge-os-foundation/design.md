## Context

四条导出线已经产出 5082 个 Markdown 文件、6546 万字符（约 4360 万 token）、189MB，其中带正文可进 Vault 的约 4900 篇。这个规模决定了本设计的大部分取舍：切成 chunk 约 8~9 万条，属于"小语料"，专业向量库与独立全文搜索引擎在这个量级上提供不了可感知的收益，却要付出常驻服务的运维成本。

现状的三个具体问题：

**frontmatter 四条线各说各话。** 微信是 `account/favorite_time/favorite_id`，Chrome 是 `site/folder/bookmark_time/bookmark_id`，掘金文章是 `author/category/tags/digg_rank`，小册是 `book/chapter/order_source`。没有统一 id，没有统一来源模型，`tags` 只有一条线有。

**分类靠关键词正则，尾部很长。** 微信 1540 条、Chrome 715 条落进「99-待确认」，约占四成。现有的 12 个一级类目是人工拍的，不是从语料归纳的。

**完全没有检索能力。** 唯一的查找方式是 `grep` 和目录浏览。

约束：单人使用；本机运行，不接受常驻基础设施；已确认内容可以发送给云端模型；本仓库是公开仓库，而 Vault 内容是他人版权材料。

## Goals / Non-Goals

**Goals:**

- 4900 篇文档收敛成一套 frontmatter schema，在 Obsidian 中按主题可浏览
- 主题体系从语料本身归纳，而不是沿用拍脑袋的 12 类
- 提供混合检索，并在 Cursor 中通过 MCP 直接可用
- 检索过程可观测，每次检索的中间状态可查
- 检索质量有量化标准，改动前后可比较
- 索引层随时可删除重建，不承载任何业务数据
- 为替换向量库、全文引擎、嵌入模型留出接口，但第一版不实现替换

**Non-Goals:**

- 后台管理界面、AI Chat（独立的后续 change）
- 文件监听与自动增量索引（独立的后续 change，本 change 只提供手动触发的增量命令）
- 知识图谱、实体抽取、Agent 编排、重排序模型
- PDF / URL / GitHub 的在线导入（本 change 只做存量迁移，新内容仍走现有四条 Python 线）
- 多用户、鉴权、云端部署

## Decisions

### D1：Vault 放在独立的私有仓库

Vault 装的是公众号文章、掘金文章和付费小册——他人的版权内容。本仓库是公开的 MIT 仓库，这些内容进去就是在分发别人的作品。

考虑过的替代方案：放进本仓库并 gitignore（那样 Vault 就没有版本历史和同步，而这恰恰是 Obsidian 用户最需要的）；把整个仓库转私有（放弃开源展示）；用 git submodule（目录上好看，代价是 submodule 的日常麻烦，而两边的提交节奏完全不同，强行绑定没有收益）。

选择独立私有仓库，本仓库只存 `VAULT_PATH` 配置。两边生命周期彻底解耦：代码可以公开演进，数据始终私有。

### D2：顶层按「读的」与「写的」分区

`Library/` 装的是 4900 篇别人写的原文，`Notes/` 装的是自己的概念笔记（一个概念一篇）。这两种东西性质完全不同：前者是只读素材、量大、机器维护；后者是自己的产出、量小但价值密度高、机器不能碰。混在同一棵目录树下，想看「我对 Permit2 的理解」会点开一堆别人写的 Permit2 文章。

所以顶层按归属分区：机器维护区是 `Inbox/`、`Library/`、`Books/`、`Maps/`，手写区是 `Notes/`、`Projects/`、`Daily/`、`Templates/`。`Inbox/` 与 `Projects/` 在本 change 中只是建立目录并纳入索引范围——`Inbox/` 的填充由后续的导入 change 负责，`Projects/` 始终由人手写。

原方案里这个目录叫 `Knowledge/`，改名 `Library/` 是为了消歧：**Library 是资料，Notes 才是知识**。两者以后会互相引用（在 `Notes/Permit2.md` 里链到 `Library/` 下的几篇原文），这是系统真正产生价值的地方，因此命名上必须一眼能分开。改名在实现开始前完成，零成本。

### D2a：主题目录树，配三项缓解措施

用户明确希望在文件树里按主题逐篇浏览，因此 `Library/` 的物理目录按主题组织。但按主题建目录有三个真实代价，各自需要对策：

*一篇文档常属于多个主题，而目录只能放一处。* 对策是 `topics[0]` 决定目录，完整的主题列表保留在 frontmatter 中，并由 `Maps/<主题>.md` 索引页覆盖全部主题。目录是主视图，Maps 是补充视图。

*重新分类会移动文件，打断一切基于路径的引用。* 对策见 D3。

*12 个一级类目平均 400+ 篇，单目录撑爆。* 对策是必须切到二级，目标每个叶子 20~80 篇，并在归纳阶段对超过 150 篇或少于 10 篇的叶子给出提示。

考虑过的替代方案是按来源加时间存放、主题完全走标签与 Maps。那样路径天然稳定，但牺牲了用户明确要的浏览体验；加上 D3 之后，目录树方案的主要风险已经被消化。

### D3：永久 id 作为系统的锚

每篇文档有一个永不变的 `id`，索引、检索引用、去重、跨文档链接全部以它为键；`id → 路径` 的映射存在索引库里，扫描 Vault 时按 frontmatter 中的 `id` 更新。Obsidian 内部链接统一用 `[[文件名]]` 而非路径，Obsidian 在移动文件时会自行修复。

这样重新分类的代价从"所有引用失效"降到"重跑一次扫描"。这是 D2 能够成立的前提。

### D4：主题体系由语料归纳，但必须经人工确认

做法是为每篇文档生成一个文档级向量（标题 + 摘要 + 标题大纲），聚类后让 LLM 为每个簇命名，产出带文档数与样本标题的候选体系，停下来等人工审核，确认后才执行分类与写入。

文档级向量与 P1 检索用的 chunk 级向量是两批独立数据，不能相互复用——前者要的是"这篇整体在讲什么"，后者要的是"这一段在讲什么"。好在文档级向量很便宜：4900 篇每篇几百 token，一次约 $0.05。

之所以设人工闸门：这棵目录树是以后每天要看的东西，让 LLM 一把梭直接铺开 4900 个文件，返工成本远高于审核一份候选清单的成本。

之所以不沿用现有 12 类：它是关键词正则时代的产物，四成内容归不进去。语料的实际分布（前端占绝对多数、Web3 与 AI 各成一块）应该由语料自己说了算。

体系一经确认就固化成配置文件，之后只做增量分类——否则每次重跑都可能得到不一样的目录树。

### D5：自己实现检索循环，不用 RAG 框架

核心循环大约 600 行：remark 切块、批量嵌入、双路召回、RRF 融合。

考虑过 LlamaIndex TS。它的价值集中在几十种 reader、retriever 和 agent 抽象，而这里只有一种数据源（自己的 Markdown）、一种检索策略，90% 的能力用不上。更关键的是本 change 明确要求检索过程可观测——框架的抽象层恰恰会把 chunk 与打分过程藏起来。另外 context7 上 LlamaIndex TS 有 1105 个代码片段、Python 版有 30525 个，TS 版明显是较薄的一侧，遇到问题时可参考的材料少。

考虑过直接用 RagFlow 或 Dify。它们要求把知识存进自己的系统里当知识源，与"Vault 是唯一事实来源"正面冲突；Vault 的变更同步会变成外挂，MCP 集成还是要自己写。它们的检索调试 UI 值得借鉴设计，但那属于后台那个 change 的事。

### D6：SQLite 一个文件同时当向量库与全文索引

`vec0` 虚拟表支持元数据列并能在 KNN 查询内直接过滤（`where topic = '前端' and k = 10`），支持 int8 与二值量化，也支持 IVF 与 DiskANN 索引。FTS5 提供 BM25。两者在同一个数据库文件里，联表取回 chunk 正文不需要跨进程。

规模已用真实语料量过，不是估算：4802 篇正文切出 **82,326 个 chunk**，1024 维 float32 合计约 322MB 裸向量，落库后 SQLite 文件约 375MB。在这个量级上实测（M 系列 Mac，暴力扫描）：全量插入 13 秒，向量 KNN top50 的 p50 约 150ms，BM25 top50 的 p50 约 116ms，带 scope/topic 过滤基本同量级。单人交互场景下这个延迟没有感知问题。

考虑过 Qdrant + Meilisearch。它们的额外能力（分布式、亿级规模、HNSW 调优）在 8 万向量这个量级用不到，代价是两个常驻服务加 Docker 运维。真正需要换的信号是明确的：语料涨到百万 chunk 级，或检索延迟超过 1 秒。

口子的形式是接口而不是框架：`VectorStore`、`TextIndex`、`Embedder` 三个接口，SQLite 与云端 embedding 只是第一组实现。换 Qdrant 意味着新增一个 `VectorStore` 实现，上层不动。

### D6a：三张表共用 rowid

`chunks`、`chunk_vec`、`chunks_fts` MUST 以同一个 rowid 对齐，增删改一律按 rowid 定位。原因是 `chunk_id` 只在 `chunks` 表上有索引：`chunk_vec` 若以它作 TEXT 主键，vec0 会把值放进 shadow 表中一个**无索引**的列；`chunks_fts` 上它是 `UNINDEXED` 列。两处按 `chunk_id` 删除都是全表扫描，导致批量建索引退化成 O(n²)——实测 8.2 万条插入耗时 429 秒，且每 2 万条的耗时从 20 秒一路涨到 193 秒。改为按 rowid 维护后同样的插入是 13 秒，且恢复线性。

两个实现细节容易踩：vec0 校验主键必须是 `SQLITE_INTEGER`，而 better-sqlite3 把 JS number 绑定为 REAL，因此 rowid MUST 以 BigInt 传入；`chunk_id` 只需被返回、从不参与过滤，声明为 auxiliary 列（`+chunk_id`）而非 metadata 列。

### D7：embedding 模型由配置决定，不绑定单一供应商

嵌入模型与维度由 `EMBEDDING_MODEL` / `EMBEDDING_DIMENSIONS` 决定，只要求供应商提供 OpenAI 兼容的 `/embeddings` 接口。实测下来这一条不是过度设计：DeepSeek 只有 chat 接口，没有 `/embeddings`（调用返回 404），而语料是中文为主，bge-m3 这类中文模型未必比 OpenAI 差。绑死任何一家都会在换供应商时波及索引层。

由此带来两个必须处理的差异：

其一，`dimensions` 请求参数只有 OpenAI 的 `text-embedding-3-*` 系列支持（matryoshka 降维），发给其他供应商会被拒绝或静默忽略。因此该字段 MUST 按模型名条件发送，而不是无条件带上。

其二，各家默认维度不同（`text-embedding-3-small` 截断后 512，`bge-m3` 固定 1024）。`vec0` 表宽度在建表时固定，维度配错会污染整张表，所以首批向量返回后 MUST 校验实际维度与配置一致，不一致立即报错并提示重建索引，而不是等到写入时才炸。

考虑过更大的模型（如 `text-embedding-3-large`）：成本高一个量级，而在中文技术文档这个场景下的增益需要黄金问题集验证之后才值得付。评测机制建好以后，换模型只是改配置再重建索引。

### D7a：chat 与 embedding 允许分属不同供应商

`CHAT_API_KEY` / `CHAT_BASE_URL` / `CHAT_MODEL` 独立于 embedding 配置，未设置时回落到 embedding 那一套。这不是为了灵活而灵活：成本结构决定了两者的选型逻辑不同——embedding 占全量成本的约 95%，chat 只有几分钱，因此 embedding 选谁取决于中文质量与价格，chat 选谁几乎只取决于手头有什么 key。强行共用一套配置，会让「embedding 用硅基流动、chat 用 DeepSeek」这种常见组合无法表达。

### D8：中文全文检索先用内置 trigram 分词器

FTS5 默认的 unicode61 会把整句中文当成一个 token，BM25 直接失效。内置的 `trigram` 分词器对中文可用，代价是索引偏大、有一定噪声，但零依赖、无需编译扩展。

考虑过带 jieba 的 `simple` 分词扩展：效果更好，但要自行编译并分发二进制扩展，与"本机能跑起来"的目标相冲突。留作升级路径——黄金问题集会告诉我们 trigram 到底拖了多少后腿，届时再决定是否值得。

要求 SQLite ≥ 3.34。

### D9：不引入 Redis、BullMQ 与 Postgres

耗时任务只有两类：全量嵌入与全量分类，都是手动触发的一次性批处理。它们需要的是断点续传，不是任务队列——而断点续传写进状态文件即可，这正是四条 Python 线已经在用的模式（`.fetch_state.json`）。元数据存 SQLite，与向量、全文同库。

引入队列的时机是出现了真正的异步触发源（比如文件监听、后台上传），那属于后续 change。

### D10：TypeScript monorepo，Python 导出线原样保留

四条导出线跑得很好，重写没有任何收益。它们搬到 `exporters/` 下继续保持标准库零依赖，与 TS 层只通过文件和 JSON 交互，不纳入 pnpm workspace。

不把它们放进 `packages/` 是因为那是 pnpm workspace 的地盘，塞入非 JS 包会让工具和读者都产生误解。

`apps/mcp` 保持为独立轻量进程，不走 Nest，因为它由 Cursor 频繁 spawn，启动开销直接影响体验。

### D10a：本 change 不建 `apps/api`

原方案在包布局里列了 `apps/api`（NestJS），同时把后台界面与 AI Chat 排除在本 change 之外——结果是建一个没有任何消费者的空骨架，只增加维护面。

`apps/api` 推迟到后台那个 change 一起引入。NestJS 仍然是选定的技术栈（练习该技术栈是用户目标之一），届时它有真正的模块要装：检索调试、文档与 topics 编辑、导入入口、索引管理。本 change 的所有能力通过命令行与 `apps/mcp` 消费，检索实现只有 `packages/retrieval` 一份，将来加 API 不需要改动它。

### D10b：手写区不要求永久 id

D3 的永久 id 解决的是「重新分类移动文件后引用不失效」。手写区不会被机器重新分类，也不会被机器写入（见 D2），所以那个问题在这里不存在。

而强制手写区带 `id` 有真实代价：要么让用户每建一篇笔记都手工填，要么让索引流程反向写入手写区文件——后者直接违背 D2 立下的边界。

因此 `Notes/`、`Projects/`、`Daily/` 以 Vault 内相对路径为身份，重命名视为删除加新增。代价只是该文档过往的检索留痕对不上，没有实质损失。想要稳定 id 的用户可以在 `Templates/` 里放一个带 `id` 字段的模板，属于用户的选择而非系统强制。

### D10c：配图随文档，不集中存放

用户希望配图统一管理、不散落在 Obsidian 默认位置。满足这个诉求的关键是「有规则」，而不是「集中」。

4900 篇文章的配图有上万张。全部落进 `Assets/images/` 会得到一个上万文件的扁平目录：Obsidian 索引变慢，文件名冲突要靠哈希前缀解决，而且删除一篇文章时无法判断它的图是否还被别处引用——不做引用计数就只能永久留着。

所以导入内容的配图随文档存在同目录的 `assets/` 下（小册那条导出线已经是这个模式，1251 张图分散在各册目录中，实践验证过），中央 `Assets/` 只服务手写区。

### D11：MCP SDK 用稳定的 v1.x

新的 `@modelcontextprotocol/server` 配 `serveStdio` 是官方推荐方向，但目前是 `2.0.0-alpha.2`。第一版用 `@modelcontextprotocol/sdk` v1.x，等 v2 稳定后再迁移——迁移面只有 `apps/mcp` 一个包，代价可控。

### D12：全部走云端模型

用户已确认接受。嵌入用 OpenAI，主题归纳与分类用 `gpt-4o-mini`。这修订了仓库原有的"不上传任何内容"原则，改为"不上传原始数据文件"。这一修订必须写进 `openspec/config.yaml` 的 context 与两份 README，否则未来的贡献者会读到互相矛盾的约定。

## Risks / Trade-offs

**LLM 归纳的主题体系不稳定，同样输入两次跑出不同结果** → 体系经人工确认后固化为配置文件，后续只做增量分类，不再重新归纳。

**4900 篇一次性分类必然有误分** → 误分的代价被限制在"目录里找不到"，检索仍能命中；`topics` 可手工修改，改后重新生成 Maps 即可。分类报告会给出「待确认」占比，超过 5% 说明体系本身需要调整。

**trigram 分词的中文 BM25 有噪声，可能拖累混合检索** → 黄金问题集提供量化依据；可分别评测纯向量、纯 BM25、混合三种模式，若 BM25 拖后腿则降低其权重或改用 `simple` 扩展。

**Vault 私有仓库含图片会很大（189MB 起步），git 对二进制不友好** → 迁移阶段决定图片策略：走 git-lfs，或只提交 Markdown、图片留在本地不入库。决策留到 P0 执行时依据实际体积做。

**黄金问题集由自己编写，存在为了通过而挑简单问题的倾向** → 问题必须在实现检索之前写好，且必须来自真实使用场景（写代码时实际想查的东西），而不是照着语料反推。

**目录搬迁会打断 git 的文件历史与文档中的路径** → 一次性完成搬迁并同步更新全部文档，`git log --follow` 仍可追溯；搬迁单独成一个提交，不与功能改动混在一起。

**成本失控** → 全量嵌入约 $0.9、全量分类约 $0.3，量级可忽略。真正的风险是反复重跑：增量索引按内容哈希判定，分类阶段支持断点续传，两者共同避免无谓的重复调用。

## Migration Plan

**P0 迁移**（本 change 第一阶段）

1. 目录搬迁与 pnpm workspace 骨架，同步更新全部文档路径
2. 归一化：四条线产出 → 统一文档记录，分配 id
3. 去重：按归一化 URL 合并（已知约 26 组跨来源重复）
4. 全量嵌入（此步产出同时供 P1 索引复用）
5. 聚类 + LLM 命名 → 候选主题体系 → **人工审核，流程在此暂停**
6. 建立 Vault 顶层骨架（含 `Inbox/`、`Projects/` 等本阶段暂空的目录）→ 分类 → 写入 `Library/` 与 `Books/` → 生成 Maps → 输出迁移报告
